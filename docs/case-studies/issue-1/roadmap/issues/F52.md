## Context

Issue #1 says "any other UI/UX framework is just a Links Notation document"
(R6) and asks that the framework is usable from React (R19) and Vue (R20).
The runtime path is the adapters: `<UiView>` in `@link-foundation/ui-react`
({{F18}}) and `UiView` in `@link-foundation/ui-vue` ({{F19}}), which mount
`ui-dom` and interpret LiNo at runtime. Teams also need an "eject to code"
path: turn a LiNo document into source files they can commit, read and edit
in their usual tools.

The research warns against **heavy code generation as the primary
architecture** (lessons from Airbnb Lona and Mitosis) and recommends "a
runtime LiNo interpreter plus thin native renderers, and codegen only for
wrappers and types"
([existing-solutions.md, recommendations C](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/existing-solutions.md)).
So exporters are a one-way convenience, never the source of truth. The
[transformer](https://github.com/link-foundation/transformer) project
describes "dialect lowering (LiNo UI to React / SwiftUI / Compose)" with LiNo
rewrite rules
([links-notation-ecosystem.md section 3](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/links-notation-ecosystem.md));
the importer {{F51}} adds a JS rule engine with the same shape that this
issue can reuse when it is merged.

## Goal

`exportDocument(source, { target, mode, componentName })` in
`@link-foundation/ui-convert` that produces readable, formatted source files
for `react`, `vue`, `swiftui` and `compose`, with golden tests, and a CLI
command to run it.

## Scope

### In scope

- Two modes for web targets:
  - `wrapper` (default): a component file that imports `UiView` from
    `@link-foundation/ui-react` or `@link-foundation/ui-vue`, inlines the LiNo
    source as a string constant and declares one stub handler per action used
    in the document (`(on press (navigate home))` → handler `navigate`).
  - `eject`: plain JSX / Vue `<template>` with semantic HTML elements
    (`<button>`, `<p>`, flex `<div>`), class names and CSS custom properties
    for tokens, plus a CSS file. Use the reverse of the {{F17}} HTML mapping
    table so import and export agree.
- Native targets (source only):
  - `swiftui`: a `struct <Name>: View` with `VStack`/`HStack`, `Text`,
    `Button`, `Toggle`, `TextField`, `.buttonStyle(.borderedProminent)` for
    `(variant filled)`;
  - `compose`: a `@Composable fun <Name>()` with `Column`/`Row`,
    `Arrangement.spacedBy(...)`, `Text`, `Button`, `Switch`, `TextField`.
  - Token references use the identifiers generated by the Swift and Kotlin
    outputs of {{F11}}; if F11 is not merged, emit literal values and a
    `// TODO token space.medium` comment.
- Unsupported kinds or props produce a comment in the output and a diagnostic
  `{ code: 'unsupported', id, target }`; the export never fails silently.
- Deterministic output, formatted (Prettier for JS/Vue; fixed 4-space
  indentation for Swift and Kotlin).
- CLI: `ui-convert export --target react|vue|swiftui|compose [--mode wrapper|eject] <file.lino>`
  writing to `--out <dir>` or stdout.

### Out of scope

- Round-trip editing (code is not read back automatically; {{F51}} imports
  JSX/Vue separately).
- React Native, Flutter and other targets (follow-ups).
- Building or running the native outputs in CI (optional check only).
- Runtime renderers ({{F22}} SwiftUI, {{F24}} Compose) — those interpret
  LiNo; this issue writes source.

## Dependencies

- {{F18}} (blocker): the public API of `@link-foundation/ui-react`
  (`UiView` props `source`, `actions`, `onAction`) used by the React wrapper
  output; its example app is used to compile-check the output.
- {{F19}} (blocker): the same for `@link-foundation/ui-vue`.
- Related: {{F17}} (package, HTML mapping table), {{F51}} (rule engine,
  round-trip test), {{F11}} (token identifiers for Swift and Kotlin),
  {{F22}}, {{F24}} (native naming conventions), {{F03}} (kind list).

## Step-by-step plan

1. In `packages/ui-convert/src/export/` create `index.js` with
   `exportDocument(source, options)` returning
   `{ files: [{ path, contents }], diagnostics }`. `source` is LiNo text or a
   `ui-core` tree; parse with `ui-core` (never with regexes).
2. `actions.js`: collect actions from `on` links:
   `collectActions(tree) -> [{ name, args }]`.
3. `react.js`: wrapper and eject generators. Wrapper example for
   `samples/document.lino`:

   ```jsx
   import { UiView } from '@link-foundation/ui-react';

   const source = `(app: document ...)`; // full LiNo text

   export function App({ actions = {} }) {
     return (
       <UiView source={source} actions={{ navigate: () => {}, ...actions }} />
     );
   }
   ```

   Escape backticks and `${` in the inlined text.

4. `vue.js`: wrapper SFC (`<script setup>` + `<UiView :source="source" />`)
   and eject SFC.
5. `swiftui.js` and `compose.js`: a kind-to-view table kept as data
   (`src/export/targets/swiftui.lino`, `compose.lino`) and a small printer.
   Expected SwiftUI shape for the sample:

   ```swift
   struct App: View {
       var body: some View {
           VStack(spacing: 16) { // TODO token space.medium
               Text("Hello, links")
               Button("OK") { actions.navigate("home") }
                   .buttonStyle(.borderedProminent)
           }
       }
   }
   ```

   Do not claim exact Swift/Kotlin API details beyond the basic views above
   without checking current Apple and Android documentation.

6. `cli.js`: add the `export` command next to the importer commands.
7. Golden tests: `tests/export/fixtures/*.lino` with expected outputs per
   target and mode (`*.react.jsx`, `*.vue`, `*.swift`, `*.kt`).
8. Compile checks: the React and Vue wrapper outputs are built by a tiny Vite
   fixture in the test; Swift and Kotlin compile checks run only when
   `swiftc` / `kotlinc` are on `PATH` and are skipped otherwise.

## Acceptance criteria

- [ ] For every fixture and target, `exportDocument` output equals the golden
      file (`node --test` golden tests).
- [ ] The React and Vue wrapper outputs build with Vite in the test and render
      the same DOM as `UiView` with the original source (jsdom comparison).
- [ ] Inlined LiNo with backticks and `${` is escaped (unit test).
- [ ] The `unsupported` fixture yields diagnostics and comments, not an
      exception.
- [ ] Output is deterministic: two runs give identical files.
- [ ] If {{F51}} is merged: importing the React eject output of `form`
      gives a tree equal to the original (round-trip test); otherwise this
      item is moved to a follow-up issue linked in the pull request.
- [ ] `npx ui-convert export --target swiftui samples/document.lino` prints
      a `struct ... : View` (CLI test).
- [ ] `npm run lint`, `npm run format:check`, `npm run check:duplication`,
      `npm test` pass.

## How to verify

```bash
node --test packages/ui-convert/tests/export/*.test.js
npm test
npm run lint && npm run format:check && npm run check:duplication
```

Optional on a machine with Xcode or a JDK: compile the generated `.swift` and
`.kt` files and attach the result to the pull request.

## Prior art and libraries

- Mitosis (MIT): JSX subset to many frameworks; learn only, note its slow
  progress.
- transformer (link-foundation): LiNo match/replace rules.
- Style Dictionary (Apache-2.0): token outputs for Swift and Kotlin (via
  {{F11}}).
- Plasmic and Builder.io codegen (learn only; avoid Plasmic AGPL code).
- Prettier (MIT) for formatting JS and Vue output.
