## Context

The Jetpack Compose / Compose Multiplatform renderer ({{F24}}) must read the same LiNo documents as the JavaScript core (R22: Kotlin support; R8: prefer links theory and LiNo). ARCHITECTURE.md plans `ui-kotlin` as a Gradle/Kotlin Multiplatform package that reads LiNo with an upstream port, or with a port created by the roadmap ([`docs/ARCHITECTURE.md`](https://github.com/link-foundation/ui/blob/main/docs/ARCHITECTURE.md), "Platforms").

State of upstream (https://github.com/link-foundation/links-notation, checked for this roadmap; re-check before starting):

- There is **no Kotlin** port, and no upstream issue asks for one.
- There is a **Java** implementation in `java/`:
  - Maven coordinates `io.github.link-foundation:links-notation` (version 0.27.1 in `java/pom.xml`);
  - `maven.compiler.release` 21, JUnit Jupiter;
  - package `io.github.linkfoundation.linksnotation`.

  It is **not published yet**: https://github.com/link-foundation/links-notation/issues/192 ("Make sure Java and Go packages are published and all CI/CD working") is open.

- `parity/text-fixtures.json` is the golden corpus: 14 cases of `{id, feature, input, expected: [{id, values}], format}`, with `id: null` for anonymous links. Java and Rust consume the generated `parity/text-vectors.tsv`, which has 4 tab-separated fields (case ID, input UTF-8 hex, expected tree, formatted UTF-8 hex), with `~` for null.
- `node scripts/ci/check-parity.mjs` requires every language in `parity/language-features.json` to have evidence, or an explicit exception in `parity/README.md`. JavaScript defines behaviour first, and all libraries are hand-written.

See section 2 of [links-notation-ecosystem.md](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/links-notation-ecosystem.md).

### Options: wrap Java or port to Kotlin Multiplatform

| Option                                                                 | Works on                                                                                   | Pros                                                                | Cons                                                                                                         |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| A. Wrap the Java artifact (`io.github.link-foundation:links-notation`) | JVM and Android only. Java 21 bytecode on Android needs a check of current AGP/D8 support. | No new parser; upstream keeps parity                                | Blocked until issue 192 publishes it; no iOS, web or wasm, so it is useless for Compose Multiplatform on iOS |
| B. Pure Kotlin Multiplatform port (recommended)                        | All KMP targets                                                                            | One parser for Android, iOS, desktop and web; no Java 21 constraint | A ninth hand-written binding to maintain                                                                     |

Recommendation: option B, contributed upstream as `kotlin/`. While issue 192 is open, option A cannot be used at all. After it is published, an optional JVM test may compare the KMP parser with the Java one on the corpus.

## Goal

Deliver a Kotlin LiNo parser and formatter usable from Compose Multiplatform. It must pass the upstream parity corpus and the parser vectors derived from the {{F03}} fixtures. It comes with a recorded decision on wrapping Java versus a pure KMP port, and on contributing upstream versus vendoring here.

## Scope

### In scope

- The options analysis and the decision record in `docs/native-parsers.md`.
- The recommended implementation: a pure Kotlin Multiplatform module whose code is in `commonMain`, with targets `jvm`, `androidTarget`, `iosArm64`, `iosSimulatorArm64` and `iosX64`, and with `js`/`wasmJs` if the toolchain supports them (check).
- The API: `Link`, `Parser`, `ParserOptions`, `ParseException`, `formatLinks`.
- Parity tests over `text-fixtures.json` and `docs/spec/parser-vectors.json`, on every target.
- A CI job.

### Out of scope

- The element tree projection and the Compose renderer ({{F24}}).
- Streaming, the binary protocol, `LinksGroup` and `parseIndentedDocument`. Record them as exceptions, as upstream does for Python, PHP and Go.
- Publishing the Java artifact (upstream issue 192).

## Dependencies

- **{{F03}}** (blocker) provides the conformance fixtures and the decisions on limits. Start with the upstream corpus only.

Related:

- {{F24}} consumes the parser and owns the `ui-kotlin` Gradle layout.
- {{F21}} is the Swift twin. Whichever of the two lands first creates `scripts/generate-parser-vectors.mjs` and `docs/spec/parser-vectors.json` (described in {{F21}} step 8); the other reuses them.

## Step-by-step plan

1. Search the upstream issues for "kotlin". If there is none, open "Add Kotlin Multiplatform implementation", linking this issue. Propose a `kotlin/` folder, a `kotlin` entry in `language-features.json`, and Maven Central coordinates (for example `io.github.link-foundation:links-notation-kotlin`; confirm the name with the maintainer). If upstream declines or stalls, vendor the code under `native/kotlin/links-notation/` (coordinate with {{F24}}). Record the decision, the options table above and the links in `docs/native-parsers.md`.
2. Create the Gradle project:
   - Gradle wrapper, `settings.gradle.kts`, `build.gradle.kts` with `kotlin("multiplatform")`;
   - use the current stable Kotlin and Gradle (check the versions);
   - no runtime dependencies; `kotlin("test")` in `commonTest`.
3. Implement the public API in `src/commonMain/kotlin/io/github/linkfoundation/linksnotation/`:

   ```kotlin
   data class Link(val id: String?, val values: List<Link> = emptyList()) {
     fun format(): String
   }
   data class ParserOptions(val maxDepth: Int = 64, val maxInputSize: Int? = null)
   sealed class ParseException(message: String) : Exception(message) {
     class Syntax(val line: Int, val column: Int, message: String) : ParseException(message)
     class DepthExceeded(val limit: Int) : ParseException("depth > $limit")
     class InputTooLarge(val limit: Int) : ParseException("input > $limit")
   }
   class Parser(val options: ParserOptions = ParserOptions()) { fun parse(text: String): List<Link> }
   fun formatLinks(links: List<Link>): String
   ```

4. Port `js/src/grammar.pegjs` by hand as a recursive-descent parser, using common Kotlin only (no `java.*`). Iterate by code points so that Unicode cases pass. Keep the JS shapes exactly, including the multi-line path expansion noted in ARCHITECTURE.md.
5. Port the formatter and the minimal quoting rules (`js/src/references.js`, `js/src/quotes.js`).
6. Make the tests run on all targets without file I/O. Add a Gradle task `generateParityCases` that reads `parity/text-fixtures.json` and `docs/spec/parser-vectors.json` and generates `build/generated/commonTest/ParityCases.kt` (a list of `Case(id, input, expected, format, error)`). Wire it into `commonTest`'s source set.
7. Write `commonTest/ParityTest.kt`. For each case it asserts:
   - `Parser().parse(input) == expected`;
   - `formatLinks(parse(input)) == format`;
   - parsing `format` gives `expected` again.
8. Write `commonTest/SpecVectorsTest.kt`, which runs the same assertions over the F03 vectors. `error = true` cases must throw `ParseException.Syntax`.
9. Write `commonTest/LimitsTest.kt`, which covers 65 nesting levels and an input over `maxInputSize`.
10. Add CI:
    - `./gradlew jvmTest jsTest` on `ubuntu-latest` (Temurin JDK through `actions/setup-java`);
    - `./gradlew iosSimulatorArm64Test` on `macos-latest`;
    - if vendored here, use `.github/workflows/kotlin.yml`, triggered on changes to `native/kotlin/**` and `docs/spec/**`, with actions pinned by SHA.
11. If upstream: add `kotlin` to `parity/language-features.json` with evidence paths and exceptions, and pass `node scripts/ci/check-parity.mjs`.

## Files to create or change

- Upstream (preferred): `kotlin/settings.gradle.kts`, `kotlin/build.gradle.kts`, `kotlin/gradlew*`, `kotlin/src/commonMain/kotlin/io/github/linkfoundation/linksnotation/{Link,Parser,Formatter,ParseException}.kt`, `kotlin/src/commonTest/kotlin/.../{ParityTest,SpecVectorsTest,LimitsTest}.kt`, `parity/language-features.json`, `parity/README.md`, a CI workflow

## Acceptance criteria

- [ ] `docs/native-parsers.md` contains the options table, the chosen option and the link to the upstream issue or PR.
- [ ] `./gradlew allTests` passes locally on macOS; in CI the JVM and JS targets pass on Linux and the iOS simulator target passes on macOS.
- [ ] `ParityTest` covers every case of `parity/text-fixtures.json` (14 at the time of writing) for parse, format and round trip.
- [ ] `SpecVectorsTest` passes every entry of `docs/spec/parser-vectors.json`.
- [ ] `LimitsTest` proves the depth and size errors.
- [ ] `commonMain` has no `java.*` import (`grep -r "import java" src/commonMain` is empty).
- [ ] If upstream: `node scripts/ci/check-parity.mjs` passes with the `kotlin` entry.

## How to verify

```bash
cd native/kotlin/links-notation   # or kotlin/ in the upstream checkout
./gradlew allTests
grep -r "import java" src/commonMain && echo "FAIL: JVM-only import" || echo OK
cd - && node scripts/generate-parser-vectors.mjs --check
```
