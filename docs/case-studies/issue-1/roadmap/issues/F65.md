## Context

Issue #1 asks to absorb the needs of "all repositories" of the `konard`,
`deep-foundation`, `link-foundation` and `link-assistant` organisations and to
migrate their UIs to this framework over time. The
[UI projects inventory](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/ui-projects-inventory.md)
found about 95 first-party repositories with a user interface. Eight of them
have their own migration issues ({{F58}} to {{F64}}). The rest share a few
patterns:

- 15 repositories copy the `examples/universal-app` shell of
  `link-foundation/js-ai-driven-development-pipeline-template` (React 19
  without JSX, Vite, Capacitor and Electron);
- about 8 repositories copy the Deep scaffold (Next.js, Chakra UI v2,
  Capacitor, Electron);
- about 26 are vanilla HTML/JavaScript pages;
- theme toggles (about 16 repositories), settings panels (7), four different
  i18n implementations, links/graph views (10) and chat UIs (9) are
  re-implemented again and again.

Migrating a repository happens **in that repository**, so this issue does not
change their code. It delivers the plan and opens one migration issue per
repository, using the playbook from {{F57}}.

## Goal

Every first-party UI repository that is still maintained has an open
migration issue in its own repository, grouped into waves, and this repository
has a tracked list of those issues.

## Scope

### In scope

- Re-check the inventory (repositories change over time): run the listing
  commands from section 1 of the inventory and update its tables.
- Create `docs/migration/targets.lino`: one link per target repository with
  its owner, wave, stack, patterns to replace and the migration issue URL.
  Example:

  ```lino
  (calculator: target
    (repository 'link-assistant/calculator')
    (wave 1)
    (stack react vite)
    (replaces theme-toggle i18n-lino settings-panel))
  ```

- Open the migration issues, in this order (section 5 of the inventory):
  1. **Wave 1 pilots:**
     `link-foundation/js-ai-driven-development-pipeline-template` (replace
     `examples/universal-app`, so every new repository inherits the framework),
     `link-assistant/calculator`, `konard/todo`, `link-assistant/models`,
     `konard/github-pages-telegram-mini-app`.
  2. **Wave 2:** the 15 universal-app copies listed in the inventory.
  3. **Wave 3 (the parts not covered by {{F58}}–{{F64}}):**
     `link-foundation/link-cli` web, the links-notation website,
     `link-assistant/model-in-browser`, `link-assistant/react-chat-ui`.
  4. **Wave 4:** vanilla and static pages (no-build ESM bundle).
  5. **Wave 5:** the remaining Deep apps (`deep-foundation/deep`,
     `deepcase-app`, `perception-app`, `deepmemo-app`, `sdk`,
     `deepcase.github.io`), using the classic themes from {{F43}}.
- Each opened issue uses the template in the playbook from {{F57}}, links back
  to this issue, and lists the concrete files to delete (local
  `SettingsPanel`, theme toggles, i18n helpers) found in that repository.
- A generator script `experiments/migration/open-migration-issues.mjs` that
  reads `targets.lino` with `links-notation`, supports `--dry-run`, skips
  targets that already have an issue URL, and writes the URL back.

### Out of scope

- Changing code in the target repositories.
- Repositories that are archived, AI-solver log copies
  (`log-tmp-solution-draft-log-pr-*`), test repositories or copies of other
  people's projects (see the inventory's totals table).
- New renderers that no requirement asks for yet (Telegram bot keyboards,
  terminal UI). Record them in `targets.lino` with `(renderer missing …)`
  and open a separate Feature issue here if a target needs one.
- Vue, Swift and Kotlin pilots: those renderers are delivered by {{F19}},
  {{F22}} and {{F24}}; their pilots are listed in `targets.lino` only.

## Dependencies

- {{F57}}: the migration playbook and the mapping guide that every opened
  issue links to.

## Step-by-step plan

1. Read the inventory and the playbook from {{F57}}.
2. Refresh the repository listings into
   `docs/case-studies/issue-1/data/repos-<owner>.json`.
3. Write `docs/migration/targets.lino`. Validate it by parsing it with
   `links-notation` in a test (`tests/migration-targets.test.js`) that also
   checks that every target has `repository` and `wave`.
4. Write the generator script. Test the body builder with `node --test`
   (no network: inject a fake `gh` runner).
5. Run it with `--dry-run`, review the output, then run it for wave 1 only.
   Ask for review before opening waves 2–5.
6. Add `docs/migration/README.md` with a table generated from `targets.lino`
   (wave, repository, issue, status).

## Acceptance criteria

- [ ] `targets.lino` lists every maintained first-party UI repository from
      the refreshed inventory, each with a wave.
- [ ] The test parses `targets.lino` with `links-notation` and passes.
- [ ] Every wave 1 target has an open migration issue whose URL is recorded in
      `targets.lino`.
- [ ] Waves 2–5 have issues too, or this issue lists the remaining targets as
      unchecked boxes with the reason.
- [ ] `docs/migration/README.md` shows the table.

## How to verify

```bash
node --test tests/migration-targets.test.js

gh search issues --owner konard --owner link-foundation --owner link-assistant --owner deep-foundation "link-foundation/ui migration" --state open
```
