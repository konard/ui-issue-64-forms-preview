# Token taxonomy

Design tokens are named values. This framework uses three layers, a fixed set
of categories and strict naming rules, so that Material 3, Fluent 2 and
Apple-style themes (#48, #49, #50) are only different values for the same
names. The token package is implemented in #19; this page fixes the names.
The data lives in [`tokens-taxonomy.lino`](tokens-taxonomy.lino).

## Layers

| Layer     | Prefix         | Example                  | Role                                                          |
| --------- | -------------- | ------------------------ | ------------------------------------------------------------- |
| reference | `ref.`         | `ref.color.blue.40`      | Raw palette and scales. Components never read these directly. |
| system    | none           | `color.primary`          | Semantic meaning. Themes remap these to reference tokens.     |
| component | component kind | `button.container.color` | Slots of one component kind, each pointing at a system token. |

A value always flows reference → system → component. In LiNo a token refers to
another with the `(token path)` form defined by the dialect vocabulary (#11).

## Naming rules

- Paths are lower-case and dot-separated; each segment is kebab-case. Every
  path matches `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)*$`.
- The first segment of a system token is its category; reference tokens add
  `ref.` in front, component tokens start with the component kind.
- Sizes use one scale: `x-small`, `small`, `medium`, `large`, `x-large`
  (extend with `xx-` when needed). Durations use `short`, `medium`, `long`.
- Colours come in pairs: `color.X` is a fill and `color.on-X` is the content
  drawn on it; every pair must meet WCAG 2.2 AA contrast.
- Names describe a role, never a value (`color.error`, not `color.red`),
  except in the reference layer.
