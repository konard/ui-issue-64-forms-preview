## Context

Issue #1 asks that "the framework can enter a development and/or configuration
mode in which every UI/UX element can be fully configured visually" (R11) and
that we can "modify the UI/UX on the fly on any of our websites" (R9).
[`docs/ARCHITECTURE.md`](https://github.com/link-foundation/ui/blob/main/docs/ARCHITECTURE.md)
("Development/configuration mode and designer") fixes the shape: a runtime
inspector overlay, like React DevTools combined with Visual Studio's Live
Visual Tree, over the links network that every page built with the framework
already has. Every rendered element keeps a stable link ID that maps back to
its LiNo source, so selecting an element on screen selects a link.

Prior art in our own projects:

- konard.github.io already modifies its UI on the fly. Its
  `src/pages/SettingsPage.jsx` renders rows `label | control | value | ↺ reset`,
  marks changed rows with `is-changed`, has per-section and global resets and
  a "Your changes" diff box. It edits global tokens only: there is no element
  tree to select from
  ([research](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/konard-github-io-and-links-visuals.md),
  sections 2.10 and 7.5).
- formal-ai changes its UI through chat commands (`js/app/interface-commands.jsx`)
  and has a debugger view (`js/app/debugger-view.jsx`), but "there is no visual
  editor or inspector"
  ([research](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/formal-ai.md),
  sections 2.2 and 7.10).
- anime-avatar exposes a dev state handle `window.__acs = {cfg, setCfg, probe}`
  for in-app tests
  ([research](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/immortality-and-anime-avatar.md),
  pattern 22).

## Goal

A new package `@link-foundation/ui-devmode` (`packages/ui-devmode/`) that any
page rendered by `ui-dom` can enter at runtime. In dev mode the user hovers to
highlight, clicks to select, and inspects and edits the selected element in a
docked inspector. Every edit is written only to the `session` or `user`
configuration layer, never to the committed `site` layer.

## Scope

### In scope

- Three entry points: a keyboard shortcut (default `Alt+Shift+D`, ignored while
  focus is in an editable field), the `?ui-dev` URL parameter, and a
  `<ui-dev-mode>` custom element placed in the page.
- A site policy, read from the site configuration, that can disable dev mode or
  restrict entry points, writable layers and editable elements:

  ```lino
  (site-dev-mode: dev-mode
    (enabled true)
    (entry shortcut url-parameter element)
    (shortcut 'Alt+Shift+D')
    (write-layers session user)
    (locked-elements payment-form))
  ```

  With `(enabled false)` the heavy inspector code is never loaded (dynamic
  `import()` happens only after activation).

- Overlay: hover highlight box with a label (`id: type`), click to select (the
  click is captured and not delivered to the app while in pick mode), `Escape`
  leaves pick mode, a second `Escape` closes dev mode.
- Inspector, docked to the right and resizable, rendered in a shadow root so
  site styles do not leak in. Tabs:
  1. **Outline**: the element tree of the links network (tree view, keyboard
     navigable per the WAI-ARIA tree pattern), synchronised with the selection.
  2. **Properties**: property grid. Each row is
     `name | editor | resolved value | source layer | reset`. The source layer
     is one of `defaults`, `theme`, `site`, `user`, `session`. Changed rows are
     marked (the konard.github.io `is-changed` idea).
  3. **Styles**: style rules that match the element and the state they apply in.
  4. **Tokens**: tokens used by the element, with resolved value and layer.
  5. **Animations**: animations whose `target` is the element (read-only list).
  6. **Source**: the LiNo text of the selected element (read-only here).
- Typed editors chosen from the property type: number with unit, colour,
  enum (select), boolean (switch), string, token reference. Plain native inputs
  are acceptable; the controls from {{F26}} can replace them later.
- Session edits are applied live. "Save" moves the session layer into the user
  layer (persisted by ui-config). "Discard" clears the session layer. "Reset"
  on a row removes that property from the top writable layer.
- A test and agent handle: `globalThis.linkUiDevMode` with
  `{ select(id), getSelection(), setProperty(id, name, value), close() }`,
  present only while dev mode is open.

### Out of scope

- Exporting overrides, share links, agent instruction: {{F47}}.
- Moving or inserting elements, toolbox, source editing: {{F48}}.
- Editing animations and recordings: {{F49}}.
- Pages not built with the framework: {{F50}}.

## Dependencies

- {{F10}} (blocker): the layered configuration. Consumed: resolving a property
  to `{ value, layer }`, writing an override into `session` or `user`, removing
  an override, moving `session` into `user`, change events. Use the names
  merged in F10; the ones below are placeholders.
- {{F16}} (blocker): the DOM renderer. Consumed: the element-to-link-ID mapping
  (for example a `data-link-id` attribute or a `WeakMap`), the element tree, and
  incremental re-render when the configuration changes.
- Related: {{F14}} (source-preserving formatting for the Source tab), {{F12}}
  and {{F11}} (style and token resolution for the Styles and Tokens tabs),
  {{F44}} (animation list), {{F37}} (settings panel shares the editors),
  {{F05}} (Playwright and axe infrastructure).
- Work can start on the pure modules (policy, activation, outline, rows) with
  a stub config object that has the API listed in step 4.

## Step-by-step plan

1. Create `packages/ui-devmode/` with `package.json`
   (`"name": "@link-foundation/ui-devmode"`, ES module, JSDoc types), `src/`,
   `tests/` and a `README.md`, following the workspace layout from {{F01}}.
2. `src/policy.js`: `parseDevModePolicy(links)` returns
   `{ enabled, entry: Set<string>, shortcut, writeLayers, lockedElements }`
   from the `dev-mode` link of the site configuration. Defaults:
   `enabled: true`, all three entries, `write-layers session user`. Unknown
   keys produce a warning, not an error.
3. `src/activation.js`:
   `shouldActivate({ url, policy, hasElement })` (pure) and
   `installActivation({ window, policy, onActivate })` (adds the key listener,
   reads `URLSearchParams`, defines the `ui-dev-mode` custom element). The key
   listener ignores events whose target is `input`, `textarea`, `select` or
   `[contenteditable]`. Match the key with `event.code` (`KeyD`), not
   `event.key`, so the shortcut works on every keyboard layout (on macOS,
   `Alt+Shift+D` changes `event.key`).
4. `src/model.js` (pure, no DOM):
   - `buildOutline(tree)` returns `{ id, type, children }[]`;
   - `propertyRows(element, config)` returns
     `{ name, type, value, layer, changed, locked }[]`, where `config` is the
     F10 object with `resolve(id, name) -> { value, layer }`;
   - `applyEdit(config, { id, name, value, layer })` validates the layer
     against the policy and the value against the property type, then calls the
     F10 write function. Writing to `site`, `theme` or `defaults` throws.
5. `src/overlay.js`: highlight and selection boxes positioned with
   `getBoundingClientRect()`, updated on scroll, resize and re-render,
   `pointer-events: none`, respecting `prefers-reduced-motion` (no transitions).
6. `src/inspector.js` and `src/inspector.lino`: the inspector layout described
   in LiNo and rendered with `ui-dom` inside a shadow root. Tabs as in scope.
   Every visible string goes through a small message table so {{F13}} can
   localise it later.
7. `src/index.js`: `mountDevMode({ root, config, policy })` returns
   `{ open(), close(), select(id), destroy() }`; it wires activation, overlay,
   inspector and the `globalThis.linkUiDevMode` handle.
8. `examples/index.html`: a page that renders the sample document
   ([`samples/document.lino`](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/samples/document.lino))
   and mounts dev mode.
9. Unit tests (`node --test`) for steps 2–4; a Playwright test for steps 5–8.
10. Add a changeset for the new package.

## Acceptance criteria

- [ ] `parseDevModePolicy` handles the example policy above and the defaults;
      `(enabled false)` makes `shouldActivate` return `false` for every entry.
- [ ] Opening `examples/index.html?ui-dev` opens dev mode; `Alt+Shift+D` toggles
      it; the shortcut does nothing while typing in a text input.
- [ ] With `(enabled false)` no inspector module is requested over the network
      (checked in the Playwright test).
- [ ] Hovering `ok` shows a highlight labelled `ok: button`; clicking selects it
      and does not trigger its `on press` action.
- [ ] The Outline tab shows `app > body > greeting, ok` and selecting a row
      selects the element on the page.
- [ ] Changing the `ok` label in the property grid updates the page at once and
      the row shows source layer `session`; "Save" changes it to `user`; reload
      keeps the value; "Reset" restores the `site` value.
- [ ] `applyEdit` with layer `site` throws, and locked elements are read-only.
- [ ] The inspector passes axe checks and is fully usable with the keyboard.
- [ ] Screenshot of the inspector with `ok` selected attached to the pull request.
- [ ] `npm run lint`, `npm run format:check`, `npm run check:duplication`,
      `npm test` pass.

## Prior art and libraries

- React DevTools and Vue DevTools (MIT): hover highlight, select, props editing.
  Copy the UX, not the code.
- Visual Studio Live Visual Tree and Live Property Explorer: property grid of a
  running app, value source shown per property.
- click-to-component and LocatorJS: the minimal "select an element, find its
  source" flow.
- Storybook controls (MIT): property grid generated from component metadata.
- Onlook (Apache-2.0, verify): visual edits of a running app; it writes code,
  we write LiNo configuration.
- All in
  [existing-solutions.md section 3](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/existing-solutions.md).
