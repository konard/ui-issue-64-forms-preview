## Context

R23 asks that our existing projects can move to the framework easily and
that duplicated code moves into it. R15 asks that following the Google,
Microsoft and Apple guidelines makes migration from MUI easy
([requirements](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/requirements.md)).

Seven migrations follow this issue: {{F58}} konard.github.io, {{F59}}
links-visuals, {{F60}} meta-sovereign, {{F61}} formal-ai, {{F62}} deepcase,
{{F63}} anime-avatar and {{F64}} immortality. {{F65}} covers the remaining
repositories. The research shows the same problems in every one of them:

- one large stylesheet;
- settings stored as JSON in localStorage;
- hard-coded strings;
- hand-written Links Notation parsing;
- a long list of fragile UI fixes.

Each migration must keep the app working at every step. Without a shared
method, each agent will invent its own order and its own checks.

MUI is the most common React UI library. The research marks it as an
"INTEROP (migration source)" and recommends "a converter from an MUI theme to
LiNo tokens and a component-name mapping table"
([existing solutions](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/existing-solutions.md)).
deepcase's 2025 rewrite (`deep-foundation/deep`) uses MUI 6
([deepcase research](https://github.com/link-foundation/ui/blob/main/docs/case-studies/issue-1/research/deepcase.md)).
formal-ai and deepcase use Chakra.

## Goal

Write a documentation set under `docs/migration/` with three parts:

- a step-by-step playbook based on the strangler pattern;
- an MUI-to-framework mapping guide covering component names, prop names and
  theme keys;
- a checklist template that every migration issue ({{F58}}–{{F65}}) copies
  into its pull request.

## Scope

### In scope

- `docs/migration/playbook.md`: the generic procedure.
  - Phases: licence check, inventory, freezing contracts, tokens, settings,
    i18n, leaf components, screens, deletion.
  - Rules: keep the app working, take screenshots before and after, extract
    upstream first.
- `docs/migration/mui-mapping.md`: tables of MUI components, props and theme
  keys mapped to framework elements, LiNo attributes and tokens.
  - A short Chakra v2/v3 appendix, because deepcase and formal-ai use Chakra.
- `docs/migration/checklist-template.md`: a copyable checklist.
- `docs/migration/README.md`: an index of the three documents. {{F65}} later
  adds its targets table to this file.
- `docs/migration/examples/`: three small LiNo examples showing an MUI
  screen before and after (button row, form, dialog).

### Out of scope

- The MUI theme converter code and the Material 3 token set. These are in
  {{F40}}; this guide links to them.
- Automatic JSX/MUI to LiNo import. This is in {{F51}}; this guide describes
  the manual path and names the importer as optional.
- Doing any migration. Migrations are {{F58}}–{{F65}}.

## Dependencies

- **Blocked by {{F26}}**: the real element names and attribute names of the
  basic controls (button, icon button, text field, checkbox, switch, radio,
  select, slider). The mapping tables must use the exported names. Read
  `packages/ui-components/src/index.js` and copy the names; do not guess.
- **Blocked by {{F39}}**: theme documents, nesting, colour schemes and token
  names. The theme mapping section maps MUI `createTheme` keys onto them.
- A stub is possible: write the playbook and the checklist first. Neither
  needs F26/F39. Fill the mapping tables last.
- **Related:** {{F40}} (Material 3 theme and the MUI theme converter), {{F51}}
  (MUI/JSX importer), {{F27}} (dialog, menu, tabs, toast), {{F28}} (stack,
  grid), {{F29}} (lists, tables), {{F36}} (Material Symbols mapping), {{F05}}
  (visual regression infrastructure), {{F13}} (i18n), {{F15}} (settings
  schema), {{F50}} (dev mode for non-framework pages, useful during
  migration).

## Step-by-step plan

1. Create `docs/migration/README.md` with links to the three documents and
   one paragraph on when to use each.
2. Write `docs/migration/playbook.md` with these numbered phases. Each phase
   has entry criteria, actions and exit checks.
   1. **Licence gate.** Code may be copied into the framework only from
      Unlicense, CC0 or other permissive sources. If the target has no
      licence (as konard.github.io today), the owner must add one first.
   2. **Inventory.** List pages, components, stylesheets (with line counts),
      settings keys, storage keys, i18n sources and test suites. Record each
      with its file path.
   3. **Freeze contracts.** Write compatibility tests for every external
      contract before changing code: storage keys and formats, URL hashes,
      `data-*` attributes, CSS variable names, `data-testid` values, global
      hooks and events.
   4. **Baseline screenshots.** Use the target's own Playwright setup, or the
      {{F05}} harness: every page × theme × viewport.
   5. **Tokens first, zero visual change.** Move the CSS custom properties
      into a LiNo theme ({{F39}}) and generate the same variable names.
   6. **Settings as LiNo.** Use the {{F15}} schema with a reader for the old
      JSON format, kept for at least one release.
   7. **i18n.** Use {{F13}} catalogs, keeping the old `t()` signature.
   8. **Leaf components, then screens.** Use the strangler pattern: one
      component per pull request behind a thin re-export.
   9. **Delete.** Remove the old code, CSS and parsers, and record the
      line-count reduction.
3. Add a "Rules" section to the playbook:
   - each step leaves the app deployable;
   - screenshots must not differ beyond the agreed threshold, or the
     difference is explained in the pull request;
   - if the framework lacks a piece, open an issue in link-foundation/ui and
     do not fork.
4. Write `docs/migration/mui-mapping.md`, section "Components". Use one table
   with columns: MUI component, framework element ({{F26}}/{{F27}}/{{F28}}/
   {{F29}}), notes. Cover at least these 31 components:
   - Button, IconButton, TextField, Checkbox, Switch, Radio/RadioGroup,
     Select, Slider, Autocomplete;
   - Typography, Box, Stack, Grid, Container, Paper, Card;
   - Dialog, Menu, Popover, Tooltip, Snackbar, Tabs, AppBar, Drawer;
   - List, Table, Avatar, Chip, Badge, CircularProgress, LinearProgress,
     Accordion.

   Mark any MUI component with no equivalent "no equivalent yet" and link
   the issue that will add it.

5. Section "Props". Map the MUI props to LiNo attributes:
   - `variant="contained|outlined|text"` → `(variant filled|outlined|text)`
   - `color`, `size`, `disabled`, `fullWidth`
   - `startIcon` / `endIcon`
   - `onClick` → `(on press ...)`
   - `sx` → a style rule or an override link
   - `slotProps`

   Show each mapping with a JSX line and the LiNo line, for example
   `(save: button (label 'Save') (variant filled) (on press (save-document)))`.

6. Section "Theme". Map these keys to framework tokens:
   - `palette.primary.main`, `palette.mode`
   - `typography.fontFamily`
   - `shape.borderRadius`
   - `spacing`
   - `breakpoints.values`
   - `components.MuiButton.styleOverrides`, which becomes a `style` link
     ({{F12}})

   Example: `(app-theme: theme (extends material3) (token color.primary '#1976D2'))`.
   Say that conversion is automated by {{F40}}.

7. Section "Icons". MUI icons are Material Icons (Apache-2.0), which keep
   their licence and NOTICE. Map them through the {{F36}} registry by name.
8. Appendix "Chakra". Cover `ChakraProvider`/`extendTheme`, semantic tokens
   (deepcase `imports/theme/theme.tsx`, formal-ai `js/app/theme.js`) and the
   common components.
9. Write `docs/migration/checklist-template.md` with these sections, each a
   `- [ ]` list:
   - Licence
   - Inventory
   - Contracts frozen
   - Baseline screenshots
   - Tokens
   - Settings
   - i18n
   - Components (one line per component)
   - Screens
   - Deleted code (with before/after line counts)
   - New framework issues opened
10. Add `docs/migration/examples/mui-button-row.{jsx,lino}`,
    `mui-form.{jsx,lino}` and `mui-dialog.{jsx,lino}`. Parse every `.lino`
    file in a test.
11. Add `tests/docs/migration-examples.test.js`. It parses every
    `docs/migration/examples/*.lino` with `links-notation`, and checks that
    every element name used appears in the exports of
    `@link-foundation/ui-components`.

## Acceptance criteria

- [ ] The four Markdown files exist and are linked from `docs/migration/README.md`.
- [ ] The playbook has the nine phases above, each with entry criteria,
      actions and exit checks.
- [ ] `mui-mapping.md` maps at least the 31 MUI components listed in step 4.
      Each row names an exported framework element or links an issue.
- [ ] The props table covers `variant`, `color`, `size`, `disabled`,
      `fullWidth`, `startIcon`, `endIcon`, `onClick`, `sx` and `slotProps`.
- [ ] The theme table covers `palette`, `typography`, `shape`, `spacing`,
      `breakpoints` and `components.*.styleOverrides`.
- [ ] `checklist-template.md` has the 11 sections from step 9.
- [ ] `node --test tests/docs/migration-examples.test.js` passes. Every
      example parses, and every element name exists.
- [ ] No document recommends MUI X Pro/Premium or Material Web as a
      dependency.

## How to verify

ls docs/migration/
node --test tests/docs/migration-examples.test.js

horizontal scrolling at 1280 px.

## Prior art and libraries

- MUI docs (MIT core): component and theme API names. Check the current
  major version before writing the tables.
- Material 3 tokens `md.sys.*` / `md.ref.*` and material-color-utilities
  (Apache-2.0), via {{F40}}.
- Base UI (`@base-ui/react`, MIT) and Radix (MIT) part names, for the
  "notes" column.
- The strangler pattern (Martin Fowler, "StranglerFigApplication").
